# VoluMeal-Align 구현 및 검증 보고서

검토일: 2026-09-15. 요구사항 명세서 원문 및 AGENTS.md는 워크스페이스에서 발견하지 못했다. 아래 요구사항 번호는 코드 주석에 실제 존재하는 경우만 사용했다. 나머지는 구현 파일에서 추론한 기능이며 원문 요구사항으로 확정하지 않는다. 소스와 DB 데이터는 변경하지 않았다.

## 핵심 판단

프론트엔드 운영 빌드는 성공하지만 실제 API의 분석 계산은 고정 깊이와 영양 계수를 사용한다. DB와 ORM이 서로 다른 스키마를 가정하며 식단·복약 라우터는 등록되지 않았다. 단위 테스트 통과가 서비스 완성을 의미하지 않는다.

## 실행 검증

### 앞선 검토에서 확인한 결과

- backend: `python -m pytest tests -q` → 37 passed.
- frontend: `node tests/vision-contract.cjs` → PASS.
- frontend: `./node_modules/.bin/tsc --noEmit --incremental false` → 성공.
- 기존 기하 테스트는 ml/NumericalVolumeIntegrator 대상이며 실제 API의 services/GeometryIntegrator를 검증하지 않는다.
- 프론트 계약 테스트는 fixture와 대체 WebGL을 사용한다.

### 이번 추가 검증

- 운영 빌드: frontend 소스·설정을 /tmp/volumeal-review-build로 복사하고 설치된 node_modules를 연결해 `NEXT_TELEMETRY_DISABLED=1 npm run build` 실행. 종료 코드 0. 원래 개발 서버 캐시는 건드리지 않음.
- DB: `SELECT 1` 성공. information_schema.columns만 읽어 스키마 확인. 사용자/복약 레코드 본문은 조회하지 않음.
- `select(Model).limit(0)`으로 데이터 없이 SQL 호환성 검사:
  - User: users.full_name 컬럼 없음.
  - Meal: meals.image_path 컬럼 없음.
  - MealFoodItem: meal_food_items.confidence 컬럼 없음.
  - MealDrugWarning: meal_drug_warnings.medication_id 컬럼 없음.
- 실제 DB의 meals/meal_food_items/meal_drug_warnings ID는 UUID, 현재 ORM은 BigInteger. DB에는 drugs/user_medications와 medications가 함께 존재하므로 별칭으로 합치는 것은 호환되지 않음.
- TestClient에서 검출 결과만 banana 1개로 대체하고 실제 DB 조회 수행: 분석 응답 200. 이는 모델 정확도 검증이 아니라 라우트→DB→응답 경로 검증이다.
- 위 요청에 focal_length_mm=-1, conf_threshold=2를 전달해도 200, isCalibrated=true. 입력 범위 및 보정 상태 판정 오류 확인. 검출기는 대체했으므로 잘못된 threshold의 실제 추론 영향은 검증하지 않음.
- 응답을 MealEstimateResponse로 검증해도 count=5/실제 점=3 불일치가 통과함.
- GET /api/v1/meals 및 /api/v1/medications → 각각 404.
- 음식 미검출을 대체 검출기로 재현 → 422.
- 빈 이미지 업로드 → 500.
- 모듈 초기화에서 libcudnn.so.9 로딩 실패 재확인.

## 권장 수정 순서와 완료 기준

1. **기존 DB와 ORM 계약 통일**: 기존 UUID 스키마와 데이터 보존을 우선 검토한다. User/Drug/UserMedication/Meal 모델 및 관계를 복원하고 위 LIMIT 0 검사가 전부 성공해야 한다. 신규 환경에서 동일 스키마를 재현할 마이그레이션 이력을 확보한다. create_all은 기존 컬럼 변경을 해결하지 않는다.
2. **라우터·인증·저장 연결**: 모델 정합성 확인 후 meals/medications 라우터 등록. 인증된 사용자별 접근 제한, 분석 결과 저장 및 반환 ID로 재조회 검증. 식단 이미지 비저장 정책과 imageUrl 계약을 함께 확정한다.
3. **입력·응답 경계 수정**: 빈 파일, 손상 파일, 허용 용량/해상도, 초점거리와 confidence 범위를 검사한다. 음수·NaN·무한대 및 체적 경계 5/5000 안팎을 확인한다. response_model과 점군 길이·좌표·유한값 검사를 연결한다.
4. **계산 경로 단일화**: 실제 depth→intrinsics→plane→volume 경로를 API에 연결한다. 보정 유무는 실제 보정 성공에 따라 결정한다. 원시 체적을 검사한 뒤 결과를 반환한다. 음식별 밀도/영양 테이블도 한 출처로 통일한다.
5. **개인별 경고 연결**: 사용자별 활성 복약을 조회하고 음식/영양소 조건과 결합한다. 미복약 사용자, 해당 약 복용 사용자, 다른 사용자, 약 미인식 케이스를 분리한다. 규칙 출처·버전 및 문구의 적합성은 별도 검증한다.
6. **프론트 실제 데이터 표시**: GPU 상태를 서버에서 조회한다. 3D가 개략 표현이면 그렇게 명시하고, 복원이 요구된다면 응답 점군/박스를 실제 좌표로 표시한다. 컨테이너 기반 크기 조절, GPU 자원 해제, 오류 메시지 파싱과 요청 취소/시간 제한을 검증한다.
7. **모델 및 운영 검증**: ONNX와 원본 모델의 동일 이미지 출력 비교(BGR/RGB 포함), 실사진 평가셋, 실측 부피·질량 대비 오차, 동시 요청 지연과 메모리, GPU 활성 provider를 확인한다. 요구사항의 목표 수치가 없으므로 임의 합격 기준을 확정하지 않는다.

## 미검증 범위

실브라우저 WebGL/모바일 E2E, 실사진 모델 정확도, 실제 깊이 모델 성능, 대량·동시 요청, DB 쓰기/마이그레이션/시드 실행은 수행하지 않았다. 의약품 문구의 의학적 타당성을 확인한 보고서가 아니다. 요구사항 원문 확보 후 전체 항목과 수용 기준을 다시 대조해야 한다.
